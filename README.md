# NNR Dashboard — Power BI custom visuals (open template)

A **data-free, shareable template** of the NNR ("Net New Revenue") dashboard: 11 hand-built
Power BI custom visuals that render a fast, web-app-style UI (KPI tiles, period pills, drillable
coverage grids, movement waterfalls, sortable/searchable milestone tables) on top of **your own**
semantic model.

> **No data, no connection, no tenant is included.** Every visual renders purely from the Power BI
> `dataView` you bind to it. The only sample in this repo is a **fully synthetic** dataset
> (`sample/sample_dashboard_data.json`, generated by `tools/gen_sample_data.js` — fake companies,
> fake people, random numbers). The real semantic model, queries, refresh pipeline and any live feed
> are intentionally **not** part of this repo. Field/column names (the `capabilities.json` data roles)
> are *schema*, not data, so they are shared — that's how you wire your own source. See **[DATA.md](DATA.md)**.

## What you get

| Folder (`visuals/…`) | Visual | Page it drives |
| --- | --- | --- |
| `NNRAccounts`   | Accounts roll-up table (committed/uncommitted by month & quarter, Δ day/week) |
| `nNRDashboard`  | **Progress** — territory coverage grid vs target (the flagship page) |
| `NNRMilestones` | Milestone detail — searchable/sortable, deep-links a row to your CRM |
| `NNRAzure`      | Azure daily — pipeline by period + stage + owner/creator group |
| `NNROutlook`    | Outlook — committed + uncommitted vs official target, by segment/month |
| `NNRGaps`       | Territory gaps — flagged under-target territories |
| `NNRHygiene`    | Pipeline hygiene — records failing quality checks, grouped by owner |
| `NNRCapacity`   | Capacity/service-availability flagged accounts |
| `NNRSummary`    | Slide-ready summary (chunked-JSON model) |
| `NNRFrontier`   | Frontier/MACC-extended coverage (chunked-JSON model) |
| `NNRMovements`  | Milestone movement waterfall (entering/leaving a bucket) |

These are **plain TypeScript `pbiviz` visuals** (no React/framework). The whole UI — layout,
interaction, styling — is hand-rolled in each visual's `src/visual.ts` + `src/styles.ts`, so they
look and behave like a web app rather than stock Power BI.

## Prerequisites

- **Node.js 18+** (`node -v`)
- **Power BI Visuals Tools** (`pbiviz` CLI), for building from source:
  ```bash
  npm install -g powerbi-visuals-tools
  pbiviz --version
  ```
- **Power BI Desktop** (to import/use the visuals).

## Quick start

### A. Just use the prebuilt visuals (fastest)

1. Open **Power BI Desktop** → your report.
2. `File ▸ Options and settings ▸ Options ▸ Report settings (current file)` → tick
   **Developer mode / "Develop a visual"**.
3. Visualizations pane → `⋯ ▸ Import a visual from a file` → pick a `.pbiviz` from **`dist/`** → trust it.
4. Drop a **fresh** tile from the new icon and **bind the field wells** to columns in your model
   (the wells map 1:1 to that visual's `capabilities.json` roles — see **[DATA.md](DATA.md)**).
5. **Save** — that's what embeds the visual binary into the report.

### B. Build from source

```bash
cd visuals/NNRMilestones
npm install            # installs powerbi-visuals-api, typescript, d3, eslint …
pbiviz package         # -> dist/<guid>.<version>.pbiviz
```
(The `pbiviz package` "optional feature" warnings are informational and don't block the build.
To bump a version, edit **both** `version` fields in `pbiviz.json`.)

### C. See the look & feel with synthetic data (no Power BI, no real data)

Each visual ships a `build_mock.js` that reshapes the **synthetic** sample into the exact
Power BI `dataView` shape the visual consumes:

```bash
node tools/gen_sample_data.js          # (re)generate sample/sample_dashboard_data.json
cd visuals/NNRAccounts
npm run mock                            # writes testbuild/mock.js (a fake dataView)
```

The generated `sample/sample_dashboard_data.json` is also the easiest thing to load into Power BI
(via *Get Data ▸ JSON*) to get a populated, realistic preview before you wire your real model.

## Getting it into Power BI to persist (the fiddly bit, once)

Getting a custom visual to **persist** in a PBIP/PBIR report the first time must be done the
supported way (steps A.1–A.5 above). Saving writes the binary to:

```
<Report>/CustomVisuals/<guid>/resources/<guid>.pbiviz.json   (compiled JS bundle)
<Report>/CustomVisuals/<guid>/package.json
```

If you hand-edit the report JSON or copy a tile without importing, the binary isn't embedded and the
tile renders blank. Let **Desktop** write it the first time.

### Hot-swap (fast iteration after the first import)

Once a visual exists in the report you don't need to re-import on every code change:

1. Edit `src/`, bump `pbiviz.json` version, `pbiviz package`.
2. **Fully quit** Power BI Desktop (confirm `PBIDesktop`/`msmdsrv` processes are gone).
3. A `.pbiviz` is a zip — overwrite the two embedded files (back them up first):
   ```
   <Report>/CustomVisuals/<guid>/resources/<guid>.pbiviz.json  ← .pbiviz's resources/<guid>.pbiviz.json
   <Report>/CustomVisuals/<guid>/package.json                  ← .pbiviz's package.json
   ```
4. Cold-launch Desktop. New code loads, field bindings intact. (The **guid stays fixed** across
   versions — that's what lets the swap line up.) To update the **Service**, you must **publish**.

## How to feed it your own data (without sharing anyone's)

Every visual is driven by a Power BI table whose columns match its `capabilities.json` data roles.
In the original dashboard those columns come from a semantic model that flattens a single
`dashboard_data.json` contract. You reproduce that contract from **your** source:

1. Pull your pipeline/coverage data from **your** CRM / Dataverse / warehouse (MSX, Salesforce,
   a SQL model — anything).
2. Shape it to the **contract in [DATA.md](DATA.md)** — one JSON object with the documented
   top-level keys (`accounts[]`, `nnr_progress`, `territory_monthly`, `milestone_facts`, …).
3. Load it into Power BI (Get Data ▸ JSON, or a proper star model) and expose columns named like the
   data roles.
4. Bind those columns into each visual's field wells.

The `build_mock.js` in each folder is the **executable spec** for step 2/3: it shows exactly which
fields each visual reads and how they map to the field wells. Point it at the synthetic sample to see
the shape; swap in your own extract to see your data.

## Security / what was scrubbed

- `src/*.ts` render only from the bound `dataView`; there is **no embedded data**. "MSX" strings are
  UI labels and a runtime deep-link that opens whatever URL your data row carries.
- Each `build_mock.js` was **rewritten** to read the synthetic `sample/…json` (the originals pointed
  at a real local export — those paths are gone).
- `.gitignore` blocks any real `dashboard_data.json`/exports from ever being committed.
